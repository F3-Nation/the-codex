# Codex production database

## Learned Patterns

### [Deploy/Infra] Prod is the `codex` schema on the shared f3data Cloud SQL instance, and the handed-around DATABASE_URL points at a dead IP (keywords: cloud-sql-proxy, f3data, app_codex, f3_prod, DBeaver, timeout, 35.192.217.140)

- **Context**: 2026-09-22. Connecting DBeaver/psql with the `DATABASE_URL` from `.env.local` timed out for hours. The URL's host `35.192.217.140` is stale — the instance's public IP is `35.239.19.124` — and the instance's authorized-networks list blocks home IPs anyway. The app itself connects through the Cloud SQL Node connector (`src/lib/db.ts`, `DB_CONNECTION_MODE=connector`), not that URL.
- **Rule**: Reach prod through the Auth Proxy, which needs only gcloud application-default credentials on the `f3data` project (no console rights): `cloud-sql-proxy f3data:us-central1:f3data --port 5433`, then connect to `127.0.0.1:5433`, database `f3_prod`, user `app_codex`, SSL off (the proxy encrypts), search_path `codex,public`. Never print the URL or password; parse the password out of `.env.local` into `PGPASSWORD` inside a script (Python `urllib.parse.urlsplit` handles the unescaped `:`/`}` characters in it) and run psql with `PGOPTIONS="-c search_path=codex,public -c default_transaction_read_only=on"` unless you are deliberately writing. Prod is Postgres 18.4 — `UPDATE … RETURNING old.id, new.id` works.
- **Why**: The instance is shared with the whole F3 Nation stack (roles `app_auth`, `app_dashboard`, `group_readonly`, per-dev logins including `roma`); it is not a Codex-only database, and its IP allowlist is managed by the f3-nation team.

### [Contract/Schema] The migrations in this repo are not the prod schema; Drizzle in F3-Nation/f3-nation is (keywords: node-pg-migrate, migrations/, db/schema.sql, drizzle, 0027_codex_schema.sql, IF NOT EXISTS, ownership, ALTER TABLE)

- **Context**: 2026-09-22. `db/user_submissions_schema.sql` and `migrations/*.cjs` declare `id SERIAL PRIMARY KEY`, defaults, indexes and an `updated_at` trigger; prod had none of them (no PKs on six tables, no column defaults, `id` as `generated always as identity`, no triggers). Prod's `codex` schema was recreated when the app moved onto the shared instance (~Aug 2025) and is tracked by Drizzle in `F3-Nation/f3-nation` (`packages/db/drizzle/schema.ts`, migration `0027_codex_schema.sql`, PR #1059).
- **Rule**: Treat `migrations/` and `db/*.sql` as local-dev bootstrap only. Any DDL that must exist in prod has to be (1) applied directly as `app_codex` through the proxy, inside a `BEGIN … ROLLBACK` dry run first, and (2) declared in the f3-nation Drizzle schema with the migration written as a no-op for the already-present case. In that migration, `CREATE SCHEMA IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` are NOT safe no-ops — Postgres checks the privilege (CREATE on database / table ownership) before the existence short-circuit, and the f3-nation migration role owns nothing in `codex` — so guard them with `pg_namespace` / `to_regclass` lookups in a `DO` block. Verify the migration against prod by running the file as `app_codex` in a rolled-back transaction and comparing `count(*) from pg_class where relnamespace='codex'::regnamespace` before and after.
- **Why**: Merging a Drizzle migration that assumes it can alter codex objects fails at deploy with `must be owner of …` / `permission denied for database f3_prod`; and drift between what this repo's SQL says and what prod has is exactly how the duplicate-id bug below went unnoticed for a year.

### [Data] `user_submissions` ids were duplicated for a year because the identity sequence reset; repaired 2026-09-22 (keywords: user_submissions, duplicate id, sequence, user_submissions_id_remap, backup_20260922, rowCount)

- **Context**: When the table was recreated on the shared instance, `user_submissions_id_seq` restarted at 1 while 1,562 imported rows kept their ids, so every submission from Aug 2025 to Sep 2026 collided with a July-2025 `xicon_upload` import row (388 pairs). Approve/reject ran `UPDATE … WHERE id = $1`, so 350 import rows had their status flipped as collateral (35 wrongly `rejected`, not yet restored).
- **Rule**: The repair renumbered the older import row of each pair to 1563–1950, added `user_submissions_pkey`, and left `codex.user_submissions_id_remap` (old_id, new_id, created_at — keep permanently; ids appear in admin emails) and `codex.user_submissions_backup_20260922` (drop once the audit-history rollout settles). `codex.entry_tags_backup_20260922` likewise. Status updates now go through `assertExactlyOneSubmissionUpdated` in `src/lib/api.ts` (#111) — keep that guard on any new `UPDATE user_submissions` site.
- **Why**: A PK now makes a repeat impossible, but sequences are not transactional — a `setval` inside a rolled-back dry run still advances prod's sequence.

### [Data] Tags have mixed ids and `ensureTagsExist` depends on `tags_name_unique` (keywords: tags, entry_tags, ensureTagsExist, ON CONFLICT (name), gen_random_uuid, t1, Arms)

- **Context**: `codex.tags.id` is a text key with two generations: `t2`…`t20` slugs from the original import and uuids from the app's `createTagInDatabase`. `t1` was the original "Arms" tag; it was deleted and re-created as uuid `5e9da4ee-…`, stranding 21 entries until 2026-09-22's cleanup remapped them. `ensureTagsExist` (`src/lib/api.ts`) inserted new tags by name only with `ON CONFLICT (name)`, which prod could not satisfy (no unique on `name`) — creating an entry with a brand-new tag failed in prod until #112.
- **Rule**: Prod now has `tags_pkey (id)` and `tags_name_unique (name)`, and `entry_tags` has `entry_tags_pkey (entry_id, tag_id)` (the old `unique_entry_tag` was dropped as redundant). Always supply `gen_random_uuid()` as the id when inserting tags; never add a foreign key from `entry_tags` without first checking for orphans (`NOT EXISTS` against `tags` / `entries`) — deletes did not always clean `entry_tags` historically.
- **Why**: The app treats `name` as the human key and `id` as the join key; only the constraints keep those two consistent.

### [Tooling] `psql` in package.json was a stray npm package, not the CLI (keywords: psql, npm audit, critical, request, underscore)

- **Context**: `"psql": "^0.0.1"` sat in dependencies unused (the real `psql` is the libpq binary at `/opt/homebrew/opt/libpq/bin/psql`) and pulled in `request`, `hawk`, `underscore`, `js-yaml` 2.x — every critical finding in `npm audit`. Removed in #113 together with the `node-pg-migrate` 7→9 upgrade (`scripts/db-migrate.ts` now imports the named `runner`).
- **Rule**: If `npm audit` shows criticals again, look for a stray package before reaching for `npm audit fix --force`. The remaining highs are the `genkit`/`genkit-cli` OpenTelemetry chain with no upstream fix as of genkit 1.42.
- **Why**: The global pre-push hook blocks pushes from this repo on any critical.
